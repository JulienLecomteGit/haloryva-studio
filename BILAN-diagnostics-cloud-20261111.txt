CLIC COURT — ÉCHEC REPRODUIT ET LOCALISÉ
Job functional-x64 : Windows Server 2025 x64, bureau interactif, session 2.
Compilation du pilote réussie ; vrais hooks installés ; cible dans un processus distinct.
Clic milieu normal de référence : 1 DOWN / 1 UP.
Même fonction de rejeu native du binaire, appelée directement hors callback : retourne true ; 1 DOWN / 1 UP.
Action longue configurée : Halo : activer / arrêter ; seuil 400 ms.
Trois essais courts ciblés, aucune action longue exécutée :
- durée avant demande de relâchement : 144 / 111 / 119 ms ;
- résultat de chaque essai : +1 DOWN / +2 UP ;
- halo inchangé dans les trois essais ;
- le défaut persiste après une seconde d'attente.
Trace indépendante : le DOWN initial est retenu. À la sortie, la cible reçoit un UP avant le couple DOWN/UP réémis.
Les deux événements réémis portent le marqueur applicatif 0x43463031.
Délai entre UP simulé observé et début du rejeu marqué : environ 300 ms dans les trois essais.
Le wrapper natif fonctionne directement ; le problème apparaît lorsque le rejeu passe par le traitement de relâchement du hook.
Dans les sources preview.2 lues, InputRouter.Mouse appelle Execute -> replay -> Native.SendMouseClick avant de retourner la suppression de l'UP d'origine.
Hypothèse technique forte : ce rejeu synchrone pendant le callback retarde le retour du hook et laisse passer un UP supplémentaire.
La durée et l'ordre observés sont compatibles avec un délai d'attente Windows ; ils ne prouvent pas seuls le mécanisme exact.
La documentation Microsoft recommande un retour immédiat du hook et le report du travail hors du callback :
https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc
Limites : gestes simulés avec SendInput, observateur ajouté dans la cible, pas de souris physique ni validation Windows 11 x64 de ce défaut.
Le diagnostic n'a ni modifié le binaire ni remplacé son mécanisme de rejeu.
Le job conserve volontairement un statut d'échec ; aucune assertion assouplie.
